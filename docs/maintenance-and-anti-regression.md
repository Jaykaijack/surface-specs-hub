# Surface Specs Hub 长期维护与防返贫机制 SOP 手册 (v1.0)

> 依据《surface.kaibase.cn 网站优化改进 PRD · v1.0》§3.3、§10.5、§11 与 附录 C 编制。  
> **核心宗旨**：数据是参数资料站的生命线，品质必须沉淀为肌肉记忆。通过机器自动化硬阻断、标准化发布清单与月度定期复检机制，彻底消除单人维护带来的流程滑落风险，杜绝“改完就忘、发完就乱、时间一长回到解放前”的返贫反模式。

---

## 一、 防返贫核心原则与站长铁律

1. **机器守门，绝不依靠人工记忆 (R-1 风险防线)**
   - 任何更新发布前，必须完整运行 `node scripts/preflight_check.js` 预发布流水线与 `node tests/test-runner.js` 全量自动化测试。
   - 只要有 1 项检查未通过（非零退出码），发布动作必须立即中止，严禁绕过流水线强制上线。

2. **零幻觉与可追溯政策 (Zero-Hallucination Policy)**
   - 严禁脑补、杜撰任何未公开或未证实的参数。
   - 所有在售与历代机型参数必须源于微软官方商用产品规格表、微软在线商城、微软支持文档或官方发布会 Keynote。
   - 官方未披露的参数统一使用 `Catalog.specState` 标准空态：`NOT_DISCLOSED`（官方未披露）、`NOT_APPLICABLE`（不适用）或 `NULL`（—）。

3. **客观中立表述 (Anti-Slop & Anti-Hype)**
   - 彻底摒弃电商导购式营销夸大修饰词（如“巅峰”、“极致”、“绝无仅有”、“史上最强”等）。
   - 以严谨的实测数据、芯片物理架构与实测续航为核心叙事，守护民间第三方资料库的中立公信力。

4. **版本不可变性 (Immutable Release Snapshot)**
   - 每次版本迭代必须递增语义化版本号（Semantic Versioning）。
   - 每次构建产物必须保存至 `releases/surface-specs-hub-standalone-v<VERSION>-<DATE>-<DESCRIPTOR>.html`，根目录保留稳定指针，禁止无痕覆盖。
   - 强制在 `CHANGELOG.md` 中按规范登记变更理由与明细。

## 二、 T-7 预发布流水线五项拦截检查

`scripts/preflight_check.js` 是站点的第一道自动化防线。每次更新代码或规格数据后必须在命令行执行：

```bash
node scripts/preflight_check.js
```

### 五项硬阻断拦截标准

| 序号 | 检查维度 | 判定红线 | 处置动作 |
| :--- | :--- | :--- | :--- |
| **1** | **内部编辑备注扫描** | 源码与数据中禁止出现「官方写了上市月份」、「图片待核验」、「内部备注」等工作批注。 | 命中即硬阻断，输出具体文件与行号。 |
| **2** | **术语合规性扫描** | 芯片命名（高通骁龙® X2、英特尔® 酷睿™ Ultra）、NPU 算力（`数字 + 空格 + 大写 TOPS`，如 `80 TOPS`）。严禁未证实的爆料词（如 RTX Spark）。 | 格式不符即硬阻断，指出预期格式。 |
| **3** | **极限词零容忍扫描** | 全站禁止出现「巅峰」、「极致」、「绝无仅有」、「史上最」、「全行业最」、「独步天下」。 | 命中即硬阻断，强制要求中性化改写。 |
| **4** | **图片 alt 一致性检查** | 全量机型配图必须存在非空 alt；严格对齐机型名称、屏幕尺寸（13.8" vs 15"）与芯片架构（Intel vs 骁龙），严禁倒挂。 | 错位即硬阻断，守护 WCAG 2.2 AA 无障碍。 |
| **5** | **图片体积预算检查** | WebP 响应式资产库中：Hero/宽屏大图（w1280/w1080/w960）≤ 120KB；货架卡片/缩略图（w640/w320）≤ 40KB。 | 超标即硬阻断，强制重新压缩。 |

## 三、 附录 C · 每次发布前检查清单 (Pre-Flight Checklist)

每次准备打包发布不可变快照前，站长必须逐项对照勾选以下清单：

- [ ] **1. T-7 流水线全绿**：运行 `node scripts/preflight_check.js` 获得全部 5 项 PASS。
- [ ] **2. 全量测试全绿**：运行 `node tests/test-runner.js` 获得 5500+ 项断言全部 PASS，0 失败。
- [ ] **3. 内部批注全站 0 命中**：前台可见 HTML 与数据文件中无任何遗留标记。
- [ ] **4. 事实核验与日期同步**：本次修改的机型条目包含完整规格，`js/surface-data.js` 的 `lastVerifiedDate` 与页脚“最后核验日期”与本日同步。
- [ ] **5. 组合式计数校验**：在售与即将发售机型计数准确（如“在售 19 款 · 即将发售 4 款”），无裸“共 X 款”。
- [ ] **6. 禁用相对时间词**：前台禁止出现“今天”、“最近”、“前不久”、“刚刚发布”等模糊时间，一律使用绝对日期或月份。
- [ ] **7. 品牌去官化与声明常驻**：标题无 "Microsoft" 开头；页头标明“民间资料库（非官方）”；页脚非官方免责声明常驻可见。
- [ ] **8. 对比表决策摘要完备**：对比卡表头 3 行决策摘要（🔋续航/⚡算力与架构/⚖️重量尺寸）展示正常且有数据来源。
- [ ] **9. 结构化数据 (JSON-LD) 完备**：首页、分类页、机型详情页包含动态规范的 schema.org 数据。
- [ ] **10. 离线独立封装包构建成功**：运行 `python3 scripts/build_standalone.py` 生成带时间戳与版本号的不可变发布快照。

## 四、 月度定期复检机制 (Monthly Health Check)

固定在**每月 1 日**执行全站深度复检，防范长期运行过程中的隐性衰退：

```mermaid
flowchart LR
    A[每月 1 日定期启动] --> B[CWV 性能复测]
    B --> C[结构化数据测试]
    C --> D[全量数据健康与断链扫描]
    D --> E[微软官方在售目录对账]
    E --> F[生成复检报告并留存归档]
```

### 1. Core Web Vitals (CWV) 性能复测
- **工具**：Google PageSpeed Insights / Lighthouse
- **指标基线**：
  - 移动端 LCP ≤ 2.5s
  - INP ≤ 200ms
  - CLS ≤ 0.1
- **要求**：在移动网络模拟下测试首页、大表对比页与单机详情页，确保无性能滑坡。

### 2. 结构化数据 (Schema.org) 有效性复检
- **工具**：Google 富媒体结果测试 (Rich Results Test)
- **要求**：抽检 3 款核心机型详情页、首页与对比页，确保 `Product`、`CollectionPage` 与 `BreadcrumbList` 达到 **0 错误、0 警告**。

### 3. 微软官方国行在售目录对账 (Catalog Reconciliation)
- **比对源**：
  - 微软中国官方商城 Surface 频道 (`www.microsoftstore.com.cn/surface`)
  - 微软中国商用 Surface 门户 (`www.microsoft.com/zh-cn/surface/business`)
- **对账内容**：
  - 核查是否有新机型国行上市、配置微调或在售机型下架转入停产归档。
  - 核查即将发售机型是否已正式开售并更新状态。

### 4. 图片与资产完整性核验
- 检查是否存在 404 缺失碎图。
- 确认全量机型 Base64 内嵌编译正常，离线单文件可在断网飞行模式下顺畅交互。

## 六、 常见变更标准化作业流程 (SOP)

### SOP 1: 收录微软最新发布新机型
1. **获取官方一手规格**：
   - 提取微软官方商用/消费技术规格 PDF 或规格网页。
   - 提取官方高清渲染图，使用 `scripts/optimize_images.py` 转换为 WebP，并严格执行 Hero ≤ 120KB, 卡片 ≤ 40KB 体积预算。
2. **录入 `js/surface-data.js`**：
   - 为新机型分配语义化 `id`（如 `pro-12-13-snapdragon`）。
   - 填写 13 大类全维度参数；未知参数严格标注 `NOT_DISCLOSED`，严禁脑补。
   - 格式化处理器与 NPU 算力（如 `高通骁龙® X2 · 80 TOPS`）。
   - 更新 `lastVerifiedDate` 为录入当天日期。
3. **验证与交付**：
   - 运行 `node scripts/preflight_check.js` 确保五项拦截全绿。
   - 运行 `node tests/test-runner.js` 确保测试全绿。
   - 运行 `python3 scripts/build_standalone.py` 生成不可变版本快照。
   - 更新 `CHANGELOG.md` 并提交版本库。

### SOP 2: 在售机型转为停产/退市机型
1. 打开 `js/surface-data.js`，定位对应机型条目。
2. 将 `status` 从 `'active'` 改为 `'discontinued'`。
3. 检查分类树 `js/taxonomy.js` 与货架渲染逻辑，确认前台在售计数自动按规则重算（在售机型数减少，归档区对应增加）。
4. 运行 `node scripts/preflight_check.js` 与 `node tests/test-runner.js` 校验计数一致性。
5. 重新编译单文件发布物并记录变更日志。
